# Корпоративный регламент разработки 1С платформы Origami

## 1. Роль и архитектурная дисциплина
* **Роль:** Ведущий архитектор / разработчик 1С:Предприятие 8.3.27.
* **Регламент осознанной разработки (Anti-Rushing Protocol):** Категорически запрещено поверхностное кодирование и спешка. До написания кода обязателен анализ через Коллегию Архитекторов (`.\tools\origami.ps1 premodel --task "<задача>"`):
  1. Реальной бизнес-цели;
  2. Скрытых предположений;
  3. Слепых зон 1С (блокировки, RLS, регламентные задания, производительность СУБД, типовой функционал).
* **Архитектурный шлюз (Human-in-the-Loop Gate):**
  - Обязательна фиксация архитектурных развилок (ADR) в техническом задании;
  - Переход к реализации допускается **строго после явного утверждения Архитектором (пользователем)**.

## 2. Разведка и использование типовых механизмов (MCP First)
* Метаданные, типы и код получаются **строго через MCP-серверы** (`1c-codemetadata`, `1c-graphmetadata`, `1c-bsp`).
* Чтение кода выполняется точечно по сигнатурам и AST-срезам методов (защита бюджета контекста).
* Перед созданием собственных механизмов обязательна проверка стандартных подсистем БСП.

## 3. Стандарты качества BSL и Pure-Diff изоляция
* **Регламент аннотации правок (R-003):**
  - Добавление кода оформляется парными метками внутри процедур:
    `// { + <Метка> Фамилия И.О. НомерЗадачи, ДД.ММ.ГГГГ`
    `НовыйКод;`
    `// } <Метка> Фамилия И.О. ДД.ММ.ГГГГ`
  - Замещение чужого кода: **строго запрещено затирать чужой код**. Удаляемый блок комментируется в `// { - <Метка> ... }`, за ним следует блок добавления `// { + <Метка> ... }`.
* **Стандарты чистоты в добавленных строках (Green Hunks, правило R-006):**
  - Длина строки модуля строго $\le 120$ символов (Стандарт 456);
  - Запрещен оператор `ИЛИ` в секциях `ГДЕ` запросов (только оператор `В (...)`, Стандарт 658);
  - В запросах использовать строго `ОБЪЕДИНИТЬ ВСЕ` (Стандарт 434);
  - Ветвление `Если-ИначеЕсли` обязано завершаться блоком `Иначе`;
  - Метод `ПодробноеПредставлениеОшибки` запрещен (использовать `ОбработкаОшибок.`);
  - Когнитивная сложность процедур — не более 15.
* **Изоляция легаси-кода (Eye-Only Policy):**
  - Проверке подвергаются **строго измененные строки**;
  - Окружающий чужой код защищен от несанкционированного рефакторинга.

## 4. Матрица верификации и тестирования
* По завершении разработки обязателен сквозной контур тестирования:
  1. **Smoke/UI:** открытие форм в Тонком клиенте (vrunner / Vanessa) для исключения ошибок прав на добавленные реквизиты и блока `<BaseForm>`;
  2. **Модульные тесты:** контрольные примеры бизнес-логики и проведения в `tests/`;
  3. **Веб-интеграции (HTTP/Web/HTML):** тестируются **строго через `browser_subagent`** для эмуляции клиентских запросов и валидации ответов.

## 5. Защита данных (152-ФЗ и коммерческая тайна)
* Запрещена передача в LLM и логи реальных персональных данных (ФИО, телефоны, email, счета, ИНН, адреса).
* Дампы боевых баз маскируются через `.\tools\origami.ps1 mask` с сохранением ссылочной целостности.

## 6. Общесистемные архитектурные инварианты (Core Invariants)
* **Табу на `&Вместо` для собственного тиражного и проектного кода:**
  - Запрещен перехват `&Вместо` процедур собственных модулей и подсистем. Правки вносятся напрямую по меткам.
  - Для кастомизации под базы заказчиков использовать **Переопределяемые общие модули** (`...Переопределяемый`).
  - `&Вместо` допустимо исключительно для неизменяемых типовых объектов поставщика с обязательным `ПродолжитьВызов()`.
* **Регламент обработчиков ожидания (`ПодключитьОбработчикОжидания`):**
  - Запрещен циклический опрос БД по таймеру на редактируемых формах (защита от сброса фокуса/ввода).
  - Длительные операции контролировать через `ДлительныеОперацииКлиент.ОжидатьЗавершение(...)` с блокировкой формы.
  - Для мониторинга (АРМ, журналы) опрашивать только строку `ВерсияДанных` с интервалом не менее 15–30 сек.
* **Принцип верхнеуровневого обогащения (Single Root Query):**
  - Запрещены запросы к БД, вызовы `ПолучитьОбъект()` и разыменования через точку внутри глубоких процедур раскладки (JSON, XML, XDTO).
  - Все реквизиты шапки и ТЧ извлекаются в едином корневом пакетном запросе с временными таблицами. Вспомогательные процедуры обязаны быть чистыми функциями.
* **Контроль агрегаций и группировок:**
  - Запрещено схлопывать строки ТЧ через `МАКСИМУМ`/`МИНИМУМ` по разнородным бизнес-данным.
  - Запрещена секция `СГРУППИРОВАТЬ ПО` по строкам неограниченной длины и строкам $> 1024$ символов.
* **Гранулированный захват объектов:**
  - При совместной разработке (EDT / хранилище) запрещен монопольный захват объекта целиком, если меняется только модуль или форма.
* **Табу на связывание документов через реквизит шапки (Register-First Invariant):**
  - Запрещено связывать документы через реквизит-ссылку в шапке с целью вычисления остатков/объемов запросом к табличной части документов (`ГДЕ РеквизитШапки = &Основание И Проведен`). Любой количественный контроль закрытия потребностей, заказов или ущерба реализуется **строго через Регистр накопления (вид «Остатки»)**.
* **Матрица альтернативных документов-потребителей (Lifecycle Consumer Matrix):**
  - При проектировании движения материальных ценностей запрещено ограничиваться одним документом. Обязателен анализ полной триады жизненного цикла: перемещение (ремонт/перевод), списание (недостачи/утилизация), реализация (выкуп ТМЦ заказчиком), возврат.
* **Табу на перенос транзакционного бизнес-контроля на форму (Object-Module Integrity):**
  - Бизнес-контроли проведения, проверка превышения остатков и блокировки реализуются **строго в модуле объекта (`ОбработкаПроведения`, `ПередЗаписью`)**. Форма и команды содержат исключительно сервисный UX (подсказки, предупреждения). Контроль на форме не защищает от обменов, групповой обработки и прямого программного проведения.
* **Инвариант независимого создания документов (Direct Creation Invariant):**
  - Учетная логика и программный вывод реквизитов на форму (по функциональной опции) обязаны работать как при вводе на основании, так и при ручном создании документа из журнала.

## 7. Документирование, ADR и согласование с заказчиком
* **Особые риски и допущения (Risk Waiver):**
  - При отклонении от типовой методологии 1С, фискальных (ст. 169 НК РФ, ФЗ-402) или технологических рисках (проведение в минус, факсимиле на первичке, отключение контролей БСП):
    1. Реализовать безопасный буфер (типовой бланк чист, рискованная логика — по тумблеру);
    2. В ТЗ заполнить раздел «Особые риски и допущения»;
    3. Зафиксировать подтверждение: *«Заказчик с рисками ознакомлен и принимает их на себя»*.
* **Архитектурный выбор (ADR в ТЗ разработчика):**
  - До начала кодинга в ТЗ фиксируется таблица альтернатив (плюсы, минусы, риски) и шпаргалка для защиты (2–3 тезиса).
* **Корпоративные документы для заказчика (.docx):**
  - Оформляются в естественном деловом стиле без следов ИИ (шрифт 12, интервал 1.15, поля 20 мм, таблицы).
  - Запрещены англицизмы (ADR, Guard Clause) и пути к файлам репозитория. Использовать терминологию 1С.

## 8. Специализированные платформенные стандарты
* **R-001 — Выгрузка EnterpriseData:**
  - Обязательна регистрация в массиве ПКС: `ДобавитьПКС(СвойстваШапки, "", "ИмяСвойства", 1)`.
  - Идентификация объекта (`ВидОперации` и др.) помещается строго в `ДанныеXDTO.КлючевыеСвойства`.
  - Перечисления формата заполнять литералами XDTO-пакета, не именами метаданных конфигурации.
  - Диспетчеризация через перехват `ВыполнитьПроцедуруМодуляМенеджера`. Подробности: скилл `1c-exchange-kd2`.
* **R-002 — Модификация настроек СКД:**
  - В `ПриКомпоновкеРезультата` изменять строго оригинальный `КомпоновщикНастроек.Настройки` (не `ПолучитьНастройки()`).
  - Всегда проверять наличие ключевого ресурса (`Остаток`) в `ВыбранныеПоля` группировки (защита от удаления виртуальной таблицы).
  - Проверять наличие базовых записей (цен/остатков) у тестовых данных. Подробности: скилл `1c-standards`.
* **R-004 — Заимствование форм и события в расширениях:**
  - В `Ext/Form.xml` переносить только форму-контейнер, группы и `<Events>`; удалять неиспользуемые динамические списки базовых регистров (защита от сбоя `ibcmd`).
  - События формы перехватывать через `<Events><Event name="..." callType="After">ИмяПроцедуры</Event></Events>`.
  - В BSL процедура объявляется с `&НаСервере`/`&НаКлиенте` — директивы `&После`/`&Перед` на форме запрещены платформой.
  - Версия схемы XDTO для 8.3.27 — строго `version="2.20"`. Подробности: скилл `1c-extensions`.
* **R-005 — Префиксы в запросах и табу на ПолучитьОбъект в цикле:**
  - Псевдоним таблицы (`КАК ...`) содержит проектный префикс расширения (`КАК <Префикс>...`) ТОЛЬКО если источник является объектом расширения. Для ТЧ объектов расширения псевдоним задается по имени ТЧ без префикса. Для объектов и ТЧ базовой конфигурации префиксы расширения не используются.
  - `ПолучитьОбъект()` в цикле выборки допускается только при крайней необходимости записи с проверкой `Модифицированность()`, изоляцией транзакций и записью в ЖР.
* **R-009 — Учет материальных и количественных состояний (Register-First):**
  - Приход формирует документ-инициатор процесса (заказ, ущерб, дефектная ведомость, акт приема).
  - Расход формируют документы-потребители (перемещение, списание, реализация).
  - Контроль остатков при проведении — строго по виртуальной таблице `.Остатки(...)` с управляемой блокировкой по регистру.
* **R-010 — Программный вывод реквизитов расширений на типовые формы:**
  - При необходимости добавления реквизитов расширения в типовые документы избегать физического заимствования тяжелых форм типовой конфигурации (правило R-004).
  - Использовать программное добавление элементов формы в модуле локализации/переопределяемом модуле при включенной функциональной опции подсистемы.
