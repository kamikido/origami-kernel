# Запросы, транзакции, блокировки, обмен данными

Часть свода стандартов 1С. Сгенерировано сервером «Стандарты» — не редактировать.
Соседние темы — в таблице SKILL.md, детали по любой из них — инструмент search_knowledge.

- Вызовы начала и завершения транзакции делай парными и в одном методе — на каждый НачатьТранзакцию ровно один ЗафиксироватьТранзакцию или ОтменитьТранзакцию; начало и завершение должны быть в теле одной процедуры, а не в разных (исключение не отменяет транзакцию сразу, но запрещает её успешную фиксацию, поэтому непарность ведёт к ошибке «В этой транзакции уже происходили ошибки»).
- В транзакции выполняй только неделимые по бизнес-логике действия и держи её короткой — тяжёлые расчёты, проверку заполнения объекта и чтение без блокировки выноси до начала транзакции; порцию данных подбирай так, чтобы запись укладывалась в 20 секунд (столько по умолчанию ждётся блокировка); большие объёмы грузи порциями, а не одной длинной транзакцией.
- Не обращайся из транзакции к внешним ресурсам — сетевым папкам, сайтам, почтовым, FTP-, HTTP-, веб-сервисам: вызов может быть долгим, ресурс — недоступен, возможна ошибка тайм-аута, а блокировки всё это время держатся.
- Выбирай ровно нужные поля и данные, без «ВЫБРАТЬ * на всякий случай» — и сначала проверь, нельзя ли переложить свёртку, сортировку, вычисления на СУБД, чтобы получить готовый результат.
- Используй управляемый режим управления блокировкой данных — в нём чтение данных другими транзакциями блокируется только при несовместимых управляемых блокировках, тогда как автоматический режим даёт избыточные блокировки на уровне СУБД.
- Явную управляемую блокировку ставь перед чтением данных — если считанные данные потом будут изменяться или должны остаться неизменными до конца транзакции; блокируй только те записи, которые реально будут обработаны кодом.
- Не применяй в запросах конструкцию ДЛЯ ИЗМЕНЕНИЯ — в управляемом режиме блокировки она не имеет смысла.
- Получай все однотипные данные одним запросом, а не серией запросов в цикле — используй условие В (&Список), ОБЪЕДИНИТЬ ВСЕ или пакет запросов; запрос в цикле по списку значений медленнее обращается к базе.
- Под каждое условие запроса должен быть подходящий индекс — поля условия (ГДЕ, ПО, параметры виртуальных таблиц, ИМЕЮЩИЕ) должны идти с самого начала индекса, подряд, без «вклинивания» неучаствующих полей; иначе СУБД сканирует таблицу, запрос замедляется, растут блокировки.
- Прежде чем изменять существующий объект из кода, заблокируй его для редактирования — вызывай метод объекта Заблокировать или ЗаблокироватьДанныеДляРедактирования; иначе пользователь рискует не сохранить изменения, если те же данные конкурентно изменили в другом сеансе.
- Избегай обращения «через точку» к полям от ссылочного поля составного типа — каждый возможный тип даёт неявное соединение (Регистратор из 56 видов документов → 56 соединений) плюс соединения от ограничений доступа (RLS), что резко замедляет запрос.
- Ограничивай типы составной ссылки функцией ВЫРАЗИТЬ — ВЫБОР КОГДА Поле ССЫЛКА Документ.Имя ТОГДА ВЫРАЗИТЬ(Поле КАК Документ.Имя).Реквизит …, чтобы соединялись только нужные таблицы; либо вынеси нужный реквизит прямо в исходную таблицу (например, ДатаРегистратора в регистр), пожертвовав компактностью ради скорости.
- Не соединяй с вложенными запросами — соединяй только объекты метаданных или временные таблицы — вложенный запрос мешает СУБД оценить размер выборки и выбрать план соединения, отсюда нестабильная и местами катастрофически медленная работа; исключение — вложенный запрос сканирует мало записей.
- Объединяя результаты нескольких запросов, используй ОБЪЕДИНИТЬ ВСЕ, а не ОБЪЕДИНИТЬ — ОБЪЕДИНИТЬ тратит время на удаление полных дублей строк даже когда их заведомо нет.
- Все условия для виртуальной таблицы передавай в её параметры, а не в секцию ГДЕ — иначе СУБД может сначала выбрать всю таблицу и лишь потом отфильтровать; ограничивай выборку на самом раннем этапе.
