### ОБЯЗАТЕЛЬНЫЙ РАБОЧИЙ ПРОЦЕСС (ДИСЦИПЛИНА ИНЖЕНЕРА)

#### 1. ПЛАНИРОВАНИЕ И ИЗУЧЕНИЕ (ДО НАПИСАНИЯ КОДА):
- **Запрещен код вслепую по памяти.** Метаданные и код конфигурации заказчика – только из мсипи
  (one-s-mcp: поиск по смыслу, карточки объектов, граф связей и вызовов; навыки `1c-standards`,
  `one-s-mcp`) и только когда в мсипи активна именно эта конфигурация.
- **На вопрос «почему в этом документе так» – сначала данные базы, потом код.** Код показывает, какой
  механизм есть в конфигурации, данные – включён ли он в этой базе. Порядок: значения полей той строки,
  о которой спрашивают → заполнены ли расчётные табличные части или только итоговая с проводками →
  есть ли в базе документы-основания → есть ли настройки, на которые ссылается код (наличие, а не
  «значение по умолчанию») → только потом код. Доступа к данным нет – в ответе прямо: «вывод по коду,
  в этой базе не проверен». Для вопроса «как устроен механизм вообще» порядок обратный.
  (one-s-mcp, Binom Systems, УПП 1.3, 11.08.2026: проводку объяснили «механизмом оценочных обязательств
  по коду» – неверно целиком: расчётные части пусты, документов начисления нет, проводки пришли
  готовыми из другой системы.)
- **Разбор ошибки записи, проведения или открытия формы – сначала расширения заказчика.** В первой
  реплике назвать, какая конфигурация активна в мсипи; не та – предупредить, что выводы по типовому
  коду предварительные. Затем найти объект в расширениях заказчика (заимствован ли, формы, модули,
  `&Перед`/`&После`/`&Вместо`) и прочитать эти доработки до выводов о типовой логике. В ответе –
  строка «объект в расширениях: … / не заимствован». (Binom Systems, УТ 11.5.27, 02.10.2026: флажок
  ставила при каждом открытии заимствованная форма расширения – нашлось последним, после разбора
  только типового кода.)
- **Сначала штатное решение.** До проектирования доработки – документация ИТС по конфигурации
  заказчика и её настройки: что закрывается галочкой, ролью, вариантом отчёта, рассылкой. В ТЗ –
  разделение «настройкой / разработкой» с часами. Лучший код – тот, который не пришлось писать.
- **БСП в приоритете:** Всегда проверять типовые механизмы БСП (справочник БСП мсипи: поиск метода
  под задачу): длительные операции, файлы, строки, JSON, сообщения (`ОбщегоНазначенияКлиентСервер.СообщитьПользователю`).
- **Смотреть, как сделан типовой аналог.** Если в конфигурации уже есть похожий контроль или механизм
  (типовой запрет отгрузки, контроль задолженности), читать его реализацию в мсипи и повторять его
  приёмы: точку вызова, чтение данных, права, тексты сообщений.
- **Сверка с платформой версии заказчика:** Проверять клиент-серверный контекст (&НаКлиенте, &НаСервере, &НаСервереБезКонтекста) и поведение в фоне (синтакс-помощник мсипи).

#### 2. ЖЕСТКИЕ ПРАВИЛА ЗАПРОСОВ И РАБОТЫ С БД:
- **СТРОЖАЙШИЙ ЗАПРЕТ ЗАПРОСОВ В ЦИКЛЕ:**
  * Запрещены любые запросы, обращения к БД, получение остатков, оборотов или лимитов внутри циклов (`Для Каждого`, `Пока`).
  * ТЧ выгружается во временную таблицу: `ВЫБРАТЬ ... ПОМЕСТИТЬ ВТ_Данные ИЗ &ТаблицаДокумента`. Все проверки, остатки, лимиты и реквизиты связываются **одним пакетным запросом** с соединением к ВТ.
- **СТРОЖАЙШИЙ ЗАПРЕТ `ПолучитьОбъект()` И РАЗЫМЕНОВАНИЯ ССЫЛОК В ЦИКЛЕ:**
  * Запрещен `Ссылка.ПолучитьОбъект()` для чтения реквизитов ссылок внутри циклов.
  * Запрещено обращение через точку к полям ссылочных реквизитов ТЧ (`СтрТЧ.Ссылка.Реквизит`) — это порождает неявные SQL-запросы на каждой итерации.
  * Все необходимые поля ссылочных реквизитов (сроки действия, признаки активности/блокировки, наименования, пометки удаления) извлекаются в первичном пакетном запросе.
- **УПРАВЛЯЕМЫЕ БЛОКИРОВКИ (`БлокировкаДанных`):**
  * **Запрет перезаписи фильтра в цикле:** Вызов `Элемент.УстановитьЗначение(...)` в цикле перезаписывает измерение — блокируется только последняя строка!
  * **Блокировка по ТЧ:** Выполнять строго через `ИсточникДанных = ТаблицаДанных` и `ИспользоватьИзИсточникаДанных(...)` (см. шаблон в `1c-templates.md`).
  * Блокировка накладывается строго ДО выполнения запросов чтения остатков и лимитов.
- **Поля неограниченной длины:** Запрещено сравнивать через `=`, `<>`, `<`, `>`, группировать, сортировать. Проверка заполненности: `ПОДСТРОКА(Поле, 1, 1) <> ""` или `НЕ Поле ПОДОБНО ""`.
- **Составные ссылочные поля:** Обязательно `ВЫРАЗИТЬ(Поле КАК Тип)` перед обращением через точку.
  Проверка типа `Поле ССЫЛКА Справочник.X` допустима только для типов из состава поля – иначе запрос
  падает «Несовместимые типы "ССЫЛКА"»; для остальных – `ТИПЗНАЧЕНИЯ(Поле) = ТИП(…)`. Состав типа
  поля смотреть в мсипи до написания запроса.
- **Пометка на удаление:** В выборках действующих данных всегда указывать `ГДЕ НЕ Таблица.ПометкаУдаления`.
- **Сравнение дат со временем:** Поля со сроками действия без времени (`ДатаОкончания`) сравнивать с моментом документа через `КонецДня()`: `КонецДня(Таблица.ДатаОкончания) >= &ДатаДокумента`.

#### 3. АРХИТЕКТУРА ПРОВЕДЕНИЯ И КОНТРОЛЬ ОСТАТКОВ/ЛИМИТОВ:
- **Обязательная предварительная свёртка ТЧ:** Перед контролем остатков и движениями строки ТЧ обязаны сворачиваться по ключевым измерениям (Организация, Склад/Подразделение, Номенклатура/Объект) с суммированием количеств/сумм. Без свёртки дубли строк независимо считывают один остаток!
- **Методика проведения и перепроведение:**
  * **Запрет старой методики без очистки движений:** При перепроведении старые движения искажают остаток и лимит.
  * **Новая методика (предпочтительная):** Формирование движений $\rightarrow$ `Движения.Записать()` $\rightarrow$ проверка запросом ухода в минус (`КоличествоОстаток < 0`) по регистратору.
  * **При контроле до записи движений:** очистить старые движения текущего документа перед чтением остатков (`Движения.ИмяРегистра.Записать()`). Остатки читать строго на `МоментВремени()`, а не `Дата`.
- **Исключение текущего регистратора при проверках периодичности:** При контроле периодических регистров сведений (установка лимитов/нормативов не чаще раза в период) в запросе ОБЯЗАТЕЛЬНО исключать текущий документ: `ГДЕ Регистратор <> &Ссылка`.
- **Полнота граничных условий и `NULL`:** Отсутствие разрешающего норматива/лимита (`NULL`) или значение $\le 0$ трактуется как **запрет операции**, а не «безлимит». Проверка вида `Если Лимит > 0 Тогда ПроверитьЛимит()` категорически запрещена, если операция разрешена только при установленном значении.
  * Иной смысл пустого значения («0 – без ограничения», «нет правила – контроль выключен») допустим
    только как **решение ТЗ**, записанное словами и покрытое тестом. Молча его не подставлять.
- **Граница сравнения – в ТЗ словами.** «Просрочка больше N дней» и «не меньше N дней» – разные
  контроли. Строгость сравнения фиксируется в ТЗ и проверяется тестом ровно на граничном значении.
- **Контроль не должен зависеть от прав пользователя.** Данные для запрета (долг, остатки, лимиты)
  читать так же, как типовой контроль той же конфигурации, – как правило, в привилегированном режиме:
  ограничения доступа на уровне записей иначе скроют часть данных, и нарушение пройдёт незамеченным.
- **Роль-исключение («разрешено сверх лимита»)** проверять `РольДоступна("ИмяРоли")` вне
  привилегированного режима. `Пользователи.РолиДоступны(…)` БСП для полноправного пользователя
  всегда возвращает Истина – администратор тогда обходит любой запрет.

#### 4. РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ (МОДУЛЬ ОБЪЕКТА VS МОДУЛЬ ФОРМЫ):
- **Бизнес-логика строго в модуле объекта:** Контроль целостности, проверки заполнения, автоподбор зависимых реквизитов и актуализация связанных объектов (напр., закрытие/блокировка предыдущих статусов при создании нового) реализуются в модуле объекта (`ПередЗаписью`, `ОбработкаПроверкиЗаполнения`, `ОбработкаПроведения`), а НЕ на форме. Логика формы не срабатывает при программной записи, обмене и проведении.
- **Контроль связей на сервере:** Принадлежность зависимых аналитик (договор принадлежит контрагенту, счет принадлежит организации) валидируется в модуле объекта на сервере, а не только связью параметров выбора формы.
- **Автоподбор vs Ручной выбор:** Если вариант подстановки один — автоподбор заполняет его. Если вариантов несколько — автоподбор оставляет поле пустым, но если пользователь выбрал значение вручную, документ ОБЯЗАН провестись (после серверной проверки валидности), а не отказывать с ошибкой «найдено несколько вариантов».

#### 5. ВАЛИДАЦИЯ, СООБЩЕНИЯ И ОБРАБОТКА ОШИБОК:
- **Запрет устаревших методов:** Запрещены `Сообщить()` и `Предупреждение()`. Использовать `ОбщегоНазначенияКлиентСервер.СообщитьПользователю` или `СообщениеПользователю`.
- **Привязка к контексту:** Сообщения по строкам ТЧ обязаны содержать путь к данным с индексом строки: `Объект.ИмяТабличнойЧасти[%1].ИмяРеквизита` (где индекс = `НомерСтроки - 1`).
- **СТРОЖАЙШИЙ ЗАПРЕТ РАННЕГО `Возврат` В ЦИКЛАХ ТЧ:** Алгоритм обязан обойти ВСЕ строки ТЧ, вывести сообщения по всем проблемным строкам, выставить `Отказ = Истина`, и только после цикла завершать выполнение. Пользователь должен видеть все ошибки за один прогон.
- **Проверка заполнения:** Ключевые реквизиты шапки и ТЧ обязаны иметь `ПроверкаЗаполнения = ВыдаватьОшибку` либо проверяться в `ОбработкаПроверкиЗаполнения`.
- **Где ставить запрет проведения.** Контроль «можно ли провести» – в `ОбработкаПроверкиЗаполнения`
  (там же, где типовые контроли): сообщения привязываются к полям и видны пользователю. Отказ из
  `ОбработкаПроведения` даёт окно «Не удалось провести …» без причины. Помнить: программная
  `Записать(РежимЗаписиДокумента.Проведение)` **не вызывает** `ОбработкаПроверкиЗаполнения` –
  при программном проведении сначала `ПроверитьЗаполнение()`.
- **`СтрШаблон` + `НСтр`:** шаблон – одним литералом `НСтр`; длинный текст переносить продолжением
  строки (`|`) внутри литерала, а не склейкой нескольких `НСтр`.

#### 6. СТАНДАРТЫ СКД И ОТЧЕТОВ:
- **Параметры и фильтры:** Параметры ограничения (Организация, Период) делать обязательными (`ЗапрещатьНезаполненныеЗначения = Истина`), если отчет строится строго по ним. В наборах данных учитывать фильтры актуальности (срок действия, признак активности, не помечен на удаление).
- **Агрегация ресурсов разной детализации:** Если показатель (лимит, норматив) имеет уровень группировки «Владелец/Объект», а строки детальных записей — подчиненный разрез, запрещено простое `Сумма(Ресурс)`. Ресурс рассчитывается на уровне соответствующей группировки (`Максимум(Ресурс)`) или через `ВычислитьВыражениеСГруппировкойТаблица/Массив`.
- **Периодичность виртуальных таблиц:** Для `ОстаткиИОбороты` устанавливать периодичность `Авто`, если в группировках отчета не используется конкретное поле периода.

#### 7. ЧИСТОТА МЕТАДАННЫХ И КОМАНДНОГО ИНТЕРФЕЙСА:
- **Флаг «Вызов сервера» у общих модулей:** Ставить ТОЛЬКО если процедуры модуля вызываются напрямую с тонкого клиента. Для серверной бизнес-логики форм и объектов флаг ДОЛЖЕН БЫТЬ СНЯТ.
- **Подсистемы:** Запрещены битые ссылки (UUID без объектов). Служебные регистры не включать в корневой интерфейс подсистемы. Базовую НСИ включать в подсистемы НСИ.
- **Маски ввода:** Для фиксированных строковых форматов (ИНН, коды, номера с фиксированной длиной) задавать маску ввода на форме и проверять в модуле объекта с блокировкой при контроле уникальности.

#### 10. ОБЯЗАТЕЛЬНАЯ ПОСТ-ПРОВЕРКА (CHECKLIST ПОСЛЕ ПРАВОК):
- **Статический контроль:**
  * Отсутствие запросов, `ПолучитьОбъект()` и обращений через точку в циклах.
  * Блокировки: `ИсточникДанных` задан, нет `УстановитьЗначение` в цикле.
  * Проведение: свёртка ТЧ, исключение регистратора при периодичности (`Регистратор <> &Ссылка`), новая методика остатков.
  * Сообщения: привязаны к строкам ТЧ (`Объект.ИмяТЧ[i].ИмяРеквизита`), нет раннего `Возврат` внутри цикла.
  * Синтаксис: проверка закрытия скобок, `;` после `Возврат`, длина строк $\le 120$ символов.
- **Верификация – набор проверок из [1c-vanessa.md](1c-vanessa.md):** загрузка в базу, синтаксический
  контроль конфигуратором и применимость расширения, тесты. Инструмент – MCP `vrunner`, если он
  подключён, иначе скрипты проекта по эталону `d:\_rules\scripts` (`load_ext` → `check_ext` → `run_va`).
  Проверка синтаксиса мсипи на фрагменте – предварительная: она не видит контекста конфигурации
  и даёт ложные «не удалось разрешить модуль»; окончательное слово – конфигуратор.
  * **Петля самоисправления:** При ошибках локализовать сбой по логу/стеку, устранить причину в BSL и повторить проверку до успеха.

### СТАНДАРТЫ И ПРАВИЛА ПРОГРАММИРОВАНИЯ
1. **Обработка ошибок:** Без пустых `Попытка...Исключение`. Исключения в БД — только для блокировок. Сообщения — только средствами БСП.
2. **Форматирование:** Максимум 120 символов в строке (регламент Binom Systems), канонический порядок `#Область`.
3. **Среда:** платформа и БСП – версии заказчика (правила писались на 8.3.27; на старых платформах
   возможности ограничены его версией), русский BSL.
