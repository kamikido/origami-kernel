# Руководство по разработке и внесению изменений (Contributing Guide)

> **Проект:** Origami Platform Kernel  
> **Стандарт разработки:** [OPCES-1.1 (ГОСТ ОРИГАМИ ЯДРО 1.1)](docs/standards/origami-engineering-standard.md)

Благодарим за интерес к развитию платформы Origami Kernel. Настоящий документ регламентирует порядок внесения изменений, правила оформления кода и процесс прохождения автоматизированного контроля качества.

---

## 1. Базовые принципы контрибьюции

1. **Строгий официальный стиль:** Все описания, комментарии, документация и сообщения коммитов оформляются в официально-деловом и инженерном стиле. Любой сленг («костыли», «приколы», «колхоз») запрещен стандартом OPCES-1.1.
2. **Нулевая утечка данных (Zero-Leak):** Категорически запрещено коммитить секреты (API-ключи, пароли), персональные данные или коммерческие наименования заказчиков. Используйте параметризованные плейсхолдеры (`{{PROJECT_NAME}}`, `{{AUTHOR}}`).
3. **Стабильность downstream-проектов:** Изменения в утилитах Ядра (`tools/`) не должны нарушать работу прикладных проектов разработки 1С.

---

## 2. Порядок работы над задачей

```
1. Создание ветки ──> 2. Внесение изменений ──> 3. Контроль качества (Quality Gate) ──> 4. Pull Request
```

### 2.1. Ветвление
- Базовая стабильная ветка — `master`.
- Именование рабочих веток:
  - `feat/<краткое-описание>` — новая функциональность;
  - `fix/<краткое-описание>` — исправление дефектов;
  - `docs/<краткое-описание>` — обновление документации и плейбуков.

### 2.2. Формат коммитов (Conventional Commits)
Сообщения коммитов формируются по стандарту: `<тип>(<область>): <описание>`:
- `feat(cli): add kernel lint command to origami facade`
- `fix(lint): resolve tab-width expansion in bsl diff checker`
- `docs(playbook): add damage accounting registers canonical guide`

---

## 3. Обязательный контур верификации перед коммитом

Перед отправкой изменений в репозиторий необходимо выполнить комплексную проверку:

### 3.1. Статический контроль ядра (Zero-Leak и Style Gate)
```powershell
python tools/lint_kernel.py
```
*Утилита проверяет отсутствие API-ключей, запрещенных коммерческих названий, сленга, корректность кодировок и YAML-манифестов.*

### 3.2. Проверка BSL-кода в шаблонах и примерах
```powershell
python tools/lint_bsl_diff.py --file <путь-к-файлу> --tab-width 4
```

### 3.3. Архитектурный аудит сложных изменений
```powershell
.\tools\origami.ps1 premodel --task "<краткое описание архитектурной задачи>"
```

---

## 4. Требования к коду инструментов (`tools/`)

- **Python:** Использование стандартной библиотеки Python 3.8+ без внешних pip-пакетов. Аннотации типов (PEP 484), обработка исключений.
- **PowerShell:** Скрипты `.ps1` обязаны сохраняться в кодировке **UTF-8 с BOM** (`utf-8-sig`) и начинаться с комментария `<# ... #>`.
- **Коды возврата:** `0` — успех, `1` — ошибки валидации, `2` — критический системный сбой.

---

## 5. Добавление архитектурных плейбуков (`knowledge/playbooks/`)

Новые плейбуки оформляются строго по спецификации OPCES-1.1:
1. Заполненный YAML-frontmatter (`id`, `title`, `type`, `category`, `status: canonical`, `version`, `tags`).
2. Обязательные разделы: Контекст и риски, Архитектурное решение, Нормативная реализация BSL, Антипаттерны, Методика верификации.
3. Регистрация нового плейбука в `knowledge/playbooks/README.md`.
