# Архитектурный паттерн: Консолидация документов отгрузки и подготовка интеграционных контейнеров

> **Статус:** Одобренный корпоративный паттерн Origami Kernel  
> **Область применения:** 1С:Предприятие 8.3 (ERP, Управление торговлей, Комплексная автоматизация, WMS, TMS, интеграционные шлюзы)  
> **Категория:** Интеграция / Документооборот / Группировка данных / БСП  

---

## 1. Проблема и типичный антипаттерн разработчиков

При реализации механизмов консолидации заказов (бронирование транспорта, формирование рейсов, комплектация отгрузок) разработчики часто смешивают пользовательское представление и интеграционный обмен:

1. **Антипаттерн смешения уровней агрегации:**
   Для удобства оператора на форме строки группируются (сворачиваются). Разработчик использует этот же агрегированный набор для отправки во внешнюю логистическую систему или сервис доставки.
   * *В чем ошибка:* Внешняя система требует точной связи с каждым исходным заказом, получателем и товарной позицией. Сворачивание на уровне документа уничтожает сквозную идентификацию в интеграционном шлюзе.
2. **Антипаттерн неверного уровня хранения реквизитов (Level Mismatch):**
   Реквизиты, специфичные для конкретного заказа или получателя (например, телефон контакта, временное окно доставки, признак перевозчика), помещаются в шапку агрегированного документа или в свернутую строку. При объединении заказов разных клиентов значение одного заказа перезаписывает значение другого.
3. **Антипаттерн строкового сравнения адресов:**
   Адреса доставки сравниваются простым строковым равенством (`Адрес1 = Адрес2`).
   * *В чем ошибка:* Разные пробелы, регистр, сокращения («г.», «город», «ул.», «улица») приводят либо к ошибочному дроблению рейсов, либо к слиянию некорректных точек.

## 2. Эталонные архитектурные инварианты

### Инвариант 1. Разделение внутренней консолидации и интеграционной детализации
* Модель данных документа и модель интеграционного контейнера **явно разделены**:
  * **Пользовательский уровень (UI/Документ):** Допускает агрегацию однородных маршрутов для снижения когнитивной нагрузки оператора.
  * **Интеграционный уровень (Exchange Container):** Сохраняет детальную структуру связей: `Маршрут -> Точка -> Заказ -> Единица отгрузки -> Номенклатура`.

### Инвариант 2. Принцип минимального уровня владения реквизитом (Single Level Ownership)
Каждый реквизит обязан храниться на минимальном уровне гранулярности, где он сохраняет уникальность:

| Уровень структуры | Допустимые реквизиты | Запрещенные реквизиты |
| :--- | :--- | :--- |
| **Шапка документа** | Организация, Дата документа, Общий статус, Ответственный, Общий склад отправления | Конкретный контрагент-получатель, телефон получателя, номер отдельного заказа |
| **Строка маршрута / Точка** | Адрес точки (нормализованный), Окно доставки, Перевозчик, Последовательность объезда | Детализация товарных позиций разных заказов |
| **Единица отгрузки / Заказ** | Ссылка на Заказ клиента, Контрагент-получатель, Контактные данные получателя | Общие системные параметры рейса |
| **Строка товаров** | Номенклатура, Характеристика, Серия, Количество, Вес, Объем | Реквизиты маршрута |

### Инвариант 3. Группировка строго по составному бизнес-ключу
* Категорически запрещено группировать данные по неполным признакам (только по дате или только по складу).
* Составной ключ группировки обязательно включает все факторы совместимости:
  ```
  КлючГруппировки = СкладОтправитель + ДатаОтгрузки + ЗонаДоставки + СпособДоставки + ТипТранспорта;
  ```
* Алгоритм обязан обеспечивать диагностику разделения: оператор должен понимать, почему заказ А и заказ Б не объединились в один рейс.

### Инвариант 4. Нормализация и сравнение адресов
* Адреса сравниваются **исключительно по структурированному представлению** (компоненты адреса БСП / адресный классификатор ФИАС/ГАР / координаты / уникальный идентификатор адресного объекта).
* При строковом сравнении обязательна предварительная нормализация через функции БСП (`УправлениеКонтактнойИнформацией`).

## 3. Расширение типовых алгоритмов (Stability Invariant)

1. **Табу на подмену текста типового запроса:**
   Запрещено перехватывать и переписывать текст типового запроса БСП/конфигурации. Это приводит к гарантированным падениям при обновлении релиза вендора.
2. **Точки расширения с устойчивым контрактом:**
   Доработка выполняется через документированные точки:
   * До заполнения строки контейнера (`ПередЗаполнением...`);
   * После заполнения строки (`ПриЗаполнении...`);
   * Финальная постобработка контейнера перед сериализацией.

## 4. Чеклист архитектурной приемки (Definition of Done)

- [ ] 1. Четко разделены правила группировки строк для интерфейса и строк для выгрузки.
- [ ] 2. Реквизиты получателя и заказа не перезаписываются при объединении нескольких заказов.
- [ ] 3. Сравнение адресов доставки использует нормализованные компоненты БСП.
- [ ] 4. Реализован и протестирован сквозной сценарий: два заказа с одинаковым адресом объединяются; два заказа с разными получателями корректно сохраняют свои реквизиты.
- [ ] 5. Валидация интеграционного контейнера перед отправкой проверяет обязательные поля и блокирует отправку битых структур с понятной диагностикой ошибки.
