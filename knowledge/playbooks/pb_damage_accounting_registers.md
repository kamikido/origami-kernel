# Архитектурный паттерн: Сквозной учет материальных состояний и поврежденных ТМЦ (Register-First)

> **Статус:** Одобренный корпоративный паттерн Origami Kernel  
> **Область применения:** 1С:Предприятие 8.3 (ERP, Управление торговлей, Комплексная автоматизация, отраслевые решения аренды и сервиса)  
> **Категория:** Архитектура учетных подсистем / Проведение документов / Контроль остатков  

---

## 1. Проблема и типичный антипаттерн начинающих разработчиков

При реализации фиксации повреждений оборудования или дефектов ТМЦ (возврат из аренды, рекламация, брак при приеме) разработчики часто совершают две фундаментальные ошибки:

1. **Антипаттерн связывания документов по реквизиту (Document-Coupling):**
   В документы-потребители (например, «Перемещение товаров») добавляется реквизит-ссылка на документ фиксации дефекта. Контроль остатков и заполнение дельты пытаются делать запросом к табличной части документов:
   ```bsl
   // АНТИПАТТЕРН: попытка считать остаток по табличной части документов!
   ГДЕ ТЧ.ДокументОснование = &Основание И Документ.Проведен = ИСТИНА
   ```
   *Почему это дефект:* Не защищает от параллельных транзакций, не дает остатков на точку времени, резко замедляет СУБД при росте базы, ломается при ручном вводе документов без основания.

2. **Антипаттерн «Туннельного видения одного документа»:**
   Процесс проектируется строго под один сценарий (например, только «Перемещение на склад ремонта»). Игнорируются альтернативные исходы: списание неремонтопригодных ТМЦ или выкуп поврежденных ТМЦ клиентом.

---

## 2. Эталонное архитектурное решение (Register-First Invariant)

Учет любых материальных состояний, квот, повреждений или рекламаций строится **строго через Регистр накопления с видом «Остатки»**.

```
[Документ-Инициатор: Акт дефектов / Ущерб]
                 │
                 ▼  + Приход
 ┌───────────────────────────────────────────────┐
 │ Регистр накопления (вид: Остатки)             │
 │ Измерения: Основание, Номенклатура, Серия    │
 │ Ресурсы:   Количество                         │
 └──────────────────────┬────────────────────────┘
                        │
                        ▼  - Расход (с контролем остатков)
 ┌──────────────────────┼────────────────────────┐
 │                      │                        │
 ▼                      ▼                        ▼
[Перемещение]          [Списание ТМЦ]           [Реализация ТМЦ]
(Ремонт / Склад брака) (Утилизация / Недостача) (Выкуп клиентом)
```

### Структура регистра накопления:
* **Вид:** Остатки
* **Измерения:**
  * `ДокументОснование` (ДокументСсылка — ссылка на документ фиксации повреждения/дефекта)
  * `Номенклатура` (СправочникСсылка.Номенклатура)
  * `Характеристика` (СправочникСсылка.ХарактеристикиНоменклатуры, при наличии учета)
  * `Серия` (СправочникСсылка.СерииНоменклатуры, если для номенклатуры включен серийный учет)
  * `Склад` (СправочникСсылка.Склады, опционально)
* **Ресурсы:**
  * `Количество` (Число 15.3, неотрицательное)

## 3. Матрица жизненного цикла и документов-потребителей

Перед разработкой обязательно строится матрица хозяйственных операций:

| Хозяйственная ситуация | Документ конфигурации | Вид движения | Условия формирования |
| :--- | :--- | :--- | :--- |
| **Первичная фиксация дефекта** | Документ-инициатор (Ущерб / Акт брака) | **Приход (+)** | Всегда при проведении акта дефектов |
| **Частичный ущерб (подлежит ремонту)** | Перемещение товаров | **Расход (-)** | Перемещение на склад ремонта/реставрации |
| **Полная утрата + возмещение услугой** | Списание товаров / недостач | **Расход (-)** | ТМЦ утилизируется, клиент оплачивает услугу |
| **Полная утрата + выкуп клиентом** | Реализация товаров и услуг | **Расход (-)** | Физическая отгрузка лома/ТМЦ покупателю |

## 4. Железные платформенные инварианты

1. **Контроль строго в модуле объекта (`ОбработкаПроведения`):**
   * Все проверки лимитов и остатков выполняются в транзакции проведения документа через управляемую блокировку по регистру остатков и виртуальную таблицу `.Остатки(...)`.
   * **Запрет контроля на форме:** Форма не защищает от программного проведения, групповой обработки и обменов данными. Контроли на форме допустимы исключительно для раннего UX-предупреждения.
2. **Инвариант прямого создания документа:**
   * Документ-потребитель обязан корректно проводиться и контролировать остаток как при вводе на основании, так и при создании вручную из списка документов.
   * Единый реквизит ссылки на документ дефекта выводится на типовые формы программно при включенной функциональной опции подсистемы (без физического заимствования тяжелых форм вендора).
3. **Единообразие аналитики:**
   * Аналитика прихода и расхода обязана совпадать (для серийных товаров — контроль строго в разрезе серий, для характеристик — по характеристикам).
