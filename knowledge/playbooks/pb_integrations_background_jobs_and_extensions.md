# Архитектурный паттерн: Проектирование интеграций, фоновых заданий и безопасных расширений

> **Статус:** Одобренный корпоративный паттерн Origami Kernel  
> **Область применения:** 1С:Предприятие 8.3 (Любые конфигурации на базе БСП 3.x, ERP, УТ, КА, интеграционные модули)  
> **Категория:** Интеграция / Регламентные задания / Архитектура расширений / Оптимизация  

---

## 1. Проблема и типичный антипаттерн разработчиков

При разработке интеграционных шлюзов и обменов данными часто допускаются три критические архитектурные ошибки:

1. **Антипаттерн создания дублирующих регламентных заданий (Job Proliferation):**
   Разработчик, не изучив существующий типовой механизм обмена, добавляет собственное регламентное задание, которое опрашивает те же объекты или тот же внешний сервис.
   * *В чем ошибка:* Возникают транзакционные взаимоблокировки (deadlocks) между старым и новым заданием, задвоение запросов к внешнему API и исчерпание пула сеансов сервера 1С.
2. **Антипаттерн циклического автообновления форм без контроля версии:**
   Для отображения статуса интеграции на форме включается таймер (`ПодключитьОбработчикОжидания`), который каждые 2-3 секунды читает базу данных или вызывает сервер.
   * *В чем ошибка:* Сбрасывается фокус ввода пользователя, создается паразитная серверная нагрузка, блокируются сеансы.
3. **Антипаттерн смешения тиражного ядра и клиентских кастомизаций:**
   Специфические правила для конкретной базы или клиента «захардкоживаются» прямо в тиражные общие модули или перехватываются через директиву `&Вместо`.
   * *В чем ошибка:* Модуль теряет универсальность, ломается обратная совместимость, а `&Вместо` создает риски при обновлении конфигурации поставщика.

## 2. Эталонные архитектурные инварианты

### Инвариант 1. Architecture-First (Принцип предварительной разведки)
Перед написанием любого интеграционного кода или созданием метаданных обязательна разведка существующего ландшафта:
* Состав существующих регламентных заданий и их расписания;
* Механизмы регистрации изменений (планы обмена, версионирование, подписки на события);
* Существующие точки расширения БСП.
* **Правило:** Новое регламентное задание допускается только при доказанной невозможности использовать существующие типовые обработчики очереди интеграции.

### Инвариант 2. Разделение тиражного ядра и клиентских доработок
* Тиражные модули подсистем обязаны оставаться **чистыми и универсальными**.
* Любая проектная или клиентская вариативность реализуется через **Переопределяемые общие модули**:
  ```bsl
  // В тиражном модуле:
  ИнтеграцияКлиентПереопределяемый.ПриПолученииОтвета(ДанныеОтвета, Отказ);
  ```
* **Табу на `&Вместо`:** Директива `&Вместо` категорически запрещена для собственного проектного и тиражного кода. Изменения вносятся либо через точки расширения БСП, либо через переопределяемые модули, либо напрямую по проектным меткам.

### Инвариант 3. Регламент обработчиков ожидания на формах (UI Timer Integrity)
* Категорически запрещен циклический опрос БД по таймеру на редактируемых формах.
* Если требуется отслеживать статус длительной операции:
  1. Использовать стандартную подсистему БСП `ДлительныеОперацииКлиент.ОжидатьЗавершение(...)` с блокировкой интерфейса.
  2. Для мониторинга (АРМ, журналы документов): таймер опрашивает сервер с интервалом не менее 15–30 секунд и проверяет **строго поле `ВерсияДанных`** (или срез регистра состояния), перечитывая форму целиком только при реальном изменении версии.

### Инвариант 4. Принцип Single Root Query (Корневой пакетный запрос)
* Данные для сериализации в XML / JSON / XDTO формируются в **едином корневом пакетном запросе** с временными таблицами.
* Запрещены вызовы запросов к БД, `ПолучитьОбъект()` и разыменования через точку в цикле выборки или внутри рекурсивных процедур раскладки данных.

## 3. Чеклист архитектурной приемки (Definition of Done)

- [ ] 1. Проверено отсутствие дублирования регламентных заданий обмена.
- [ ] 2. Специфическая бизнес-логика вынесена в Переопределяемый модуль, тиражное ядро чисто.
- [ ] 3. Форма не опрашивает сервер циклически без проверки `ВерсияДанных`.
- [ ] 4. Выгрузка интеграционного пакета выполняется единым пакетным запросом без запросов в цикле.
- [ ] 5. Проверено поведение при конкурентном доступе: два фоновых задания не блокируют друг друга (используются управляемые блокировки или флаг выполнения).
